# Приём входящих сообщений

## Цель и границы

Запускать опрос уведомлений при наличии авторизованной сессии, включая восстановленную при старте приложения, и непустого списка чатов. Добавлять сообщения только в существующие чаты. Использовать поддерживаемые текущей моделью `textMessage` и `extendedTextMessage`, включая уведомления об исходящих сообщениях.

## Наблюдаемое и ожидаемое поведение

Сейчас сообщения загружаются через историю и после отправки. После изменения они также поступают из очереди уведомлений независимо от активного чата и маршрута.

## Решение и контракт

- [ReceiveNotification](https://green-api.com/v3/docs/api/receiving/technology-http-api/ReceiveNotification/): GET, ответ содержит `receiptId` и `body`, возможен пустой ответ.
- [DeleteNotification](https://green-api.com/v3/docs/api/receiving/technology-http-api/DeleteNotification/): DELETE с `receiptId` в URL; успех только при `result === true`.
- Первый запрос выполняется сразу, когда пользователь авторизован и список чатов непустой. При опустошении списка опрос останавливается; изменения сообщений и добавление других чатов не перезапускают таймер. Следующий таймер ставится на 5000 мс после завершения ReceiveNotification, включая ошибки и пустые ответы.
- При наличии receiptId удалить уведомление независимо от содержимого body и наличия чата. Успешное удаление отменяет таймер и немедленно запускает получение. Если получение уже началось по таймеру во время медленного удаления, второй параллельный запрос не запускается.
- Body обрабатывается независимо от результата удаления и наличия receiptId. Неподдерживаемые и некорректные данные пропускаются.
- При выходе, смене параметров или размонтировании остановить таймер и отменить запросы; поздние ответы игнорировать.
- Объединять загруженную историю с уже полученными сообщениями по idMessage, чтобы не терять уведомления при гонке запросов.
- Использовать feature `receive-messages` и подключение в app; setInterval не подходит, поскольку интервал должен отсчитываться от ответа.

3. Обеспечить сохранность сообщений при загрузке истории в `src/entities/chat`.
4. Проверить таймеры, ошибки, удаление, отмену, разбор и дедупликацию; оформить итоговую документацию.

## Приватность и безопасность

Не логировать тело уведомления, параметры сессии и URL с токеном. В тестах использовать вымышленные данные. Реальные API-запросы при проверках не выполнять.

## Риски и критерии приёмки

Опрос продолжается после ошибок; нет перекрывающихся ReceiveNotification и дублей сообщений; поздние ответы старой сессии не меняют state; неизвестные чаты не создаются. Медленный DeleteNotification не сдвигает обычный таймер. Нетекстовые сообщения и сервисные уведомления подтверждаются, но не отображаются в текущей текстовой модели.

## План проверки

Автоматические тесты с подменой API и времени, `npm run build`, `npm run lint`, `npm run format:check`, `git diff --check`, `git status --short`. Без браузерных проверок.
